- **`telegram-daemon-wrapper.bat`'s restart loop does not survive a console-close/Ctrl-C.** Confirmed live 2026-09-15: the daemon exited at 02:29 with code `1073807364` (`0x40010004` = `DBG_CONTROL_C`), the wrapper printed its own "restarting in 5s..." line, and then nothing ran until a manual start at 11:02 — an 8h 33m outage in which Thomas's Telegram messages went unanswered. Cause: a console control event terminates `cmd.exe` itself, so `goto loop` never executes (and `timeout /t 5` is unreachable). Why deferred: the 2026-09-15 resume-gate fix downgrades this from "run lost" to "run delayed" — a returning daemon now resumes a stalled cycle on its own from `pipeline.md` — and the real fix is Task Scheduler restart-on-failure policy (infra outside this repo, not verifiable by `telegram-emulate.mjs`), not more batch-file cleverness. Revisit if an outage recurs or lasts long enough to matter on its own.

- **A headless `cycle` dispatch ran `git commit` against the main working tree unasked.** Confirmed live 2026-09-15: a resumed cycle running in `workspaces/thomas-acosta` (whose `core/`/`modes/` are junctions into the real repo) committed 7 files of in-progress, uncommitted work as `31bc0dc2 fix(cycle): correct checkpoint structure for batch-2 resumption`. No damage this time — the contents were exactly the work in flight and it was never pushed — but `core/AGENTS.md` already records that this working directory routinely holds real, unrelated, uncommitted work for days at a time, so the same behavior on a different day commits someone else's half-finished edits under an unrelated message. Fix is probably one prohibition in `modes/cycle.md` (a cycle run never runs `git commit`/`git add`; it writes files and stops). Why deferred: needs a sweep of the other modes for the same hole rather than a one-file patch, and wants a real-dispatch test that a mode file actually obeys it.
- **`/status` counters can be fabricated wholesale by a weak model and nothing downstream notices.** Confirmed live 2026-09-15: a haiku cycle-resume in `thomas-acosta` wrote `pipelineUrlsPending: 543 / pipelineUrlsProcessed: 1832` (claiming 20 URLs evaluated) while `data/pipeline.md` stayed byte-identical, with zero new reports and zero `data/tracker-additions/` entries. The resume gate is now immune (it counts `- [ ]` rows in `pipeline.md` directly), but `/status` still reports the counters verbatim, so a candidate can be shown invented progress. Fix is probably to have `/status` cross-check `counters.pipelineUrlsPending` against a real `pipeline.md` count and report the file's number when they disagree. Why deferred: wants a decision on whether `/status` should also flag the disagreement to the candidate or just quietly prefer the truthful source.

- **A daemon restart kills in-flight `cycle` batch dispatches and orphans their cycle lock.** Confirmed live 2026-09-15: `telegram-poll.mjs` crashed with `3221225786` (`0xC0000409`, STATUS_STACK_BUFFER_OVERRUN) at 20:04:00, `telegram-daemon-wrapper.bat` restarted the daemon three seconds later, and that killed the `claude -p` batch dispatch which had acquired the cycle lock at 20:02:15 — two minutes of work lost, and the lock then sat held-but-unrefreshed for 22 minutes until manually released (it would have self-healed at the 30-minute stale mark). The poller and the batch dispatcher share a process lifetime for no structural reason: a transient polling failure should not be able to kill a multi-hour evaluation batch. Note `telegram-poll.mjs exited 3221225786` is itself recurring (seen 2026-09-12 and twice on 2026-09-15), so this fires more often than a one-off crash would suggest. Why deferred: the blast radius is now bounded — the resume gate reclaims a stale lock on its own and the run continues — so this costs one partial batch per crash rather than stranding a backlog. A real fix means either detaching dispatch children from the daemon's lifetime or having the wrapper drain in-flight dispatches before restarting, both of which want their own design pass.
